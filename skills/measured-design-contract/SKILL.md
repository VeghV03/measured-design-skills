# The contract

Any generator, in any language, satisfies this contract. The harnesses and the viewer read nothing
else. That is what makes the stack a detail.

```
generator (any stack)
   ├── boards/<id>.html      one self-contained file per screen
   └── model/*.json          eight kept files
            ↓
       build gate            every declared route must bind — refuses otherwise
            ↓
       model/index.json      generated, never edited
            ↓
   harnesses + viewer
```

## boards/

One file per screen, named `<screen id>.html`. Self-contained: no network, no shared stylesheet, no
build step to view it. It must render correctly opened straight from disk at every supported width.
A harness loads it in a headless browser and asks the DOM one question. That is the only interface.

## model/ — the eight files

These are the whole data model. **Anything not in them can never be measured.** Add a field before
you need it, not after; retrofitting means regenerating every board.

| File | Carries | Why it is separate |
|---|---|---|
| `screens.json` | id, title, kind, parent, group, widths | the IA layer |
| `journeys.json` | journeys → steps → screen ids, gates | copied verbatim from the scope document |
| `routes.json` | from, label, to, via | the only thing the gate enforces |
| `rationale.json` | screen id → why it is like this | extracted at build time, never typed twice |
| `decisions.json` | context, options, chosen, trade-off, right-if, status | the record that survives the author |
| `failures.json` | screen id → clause | which screens are trouble, and under which rule |
| `gaps.json` | step id → what nothing serves | keyed to a step, never floating |
| `policy.json` | vocabulary terms, zones, scan rules | makes the word policy checkable |

`index.json` is generated by the gate from all eight. Never hand-edit it. If it is missing, the gate
refused, and the reason is on stdout.

## screens.json — the four kinds

Every screen is exactly one kind. The classification is a design constraint, not a label.

| Kind | Definition | What it obliges |
|---|---|---|
| `place` | somewhere you can be and come back to | a nav row, a name people say aloud, and an empty state |
| `state` | a place under a condition | same route and heading as its parent; not a routing target |
| `detour` | opened, finished, returned from | must end where it started |
| `entrance` | before you are inside the product | no assumed prior state |

The gate checks the obligations: a `state` with a `parent` that is not a `place` fails; a `place`
with no screen of kind `state` carrying an empty-state marker is reported, not blocked.

## routes.json — and gesture entrances

```json
{ "from": "files-list", "label": "Move to folder…", "to": "files-move", "via": "click" }
{ "from": "files-list", "gesture": "drag row onto folder", "to": "files-move", "via": "gesture" }
{ "from": null, "to": "first-run-welcome", "via": "system" }
```

`via` is load-bearing and is the one field people leave out.

- `click` — the gate requires that `label` appears as text on board `from`. A route map that lies to
  QA is worse than a missing one. This is the only check that stops the build.
- `gesture` — drag, drop, right-click, keyboard shortcut. There is no clickable label, so the label
  check is skipped, but `to` must still resolve to a real screen id and `gesture` must be a non-empty
  description. Without this distinction every gesture-reachable screen reads as unreachable and
  someone eventually deletes it.
- `system` — reached by a condition rather than an action: first run, a push, a resumed session.
  `from` may be null.

Reachability is computed over all three. A screen with no inbound route of any kind is genuinely
unreachable and is reported.

## failures.json — the rule, written down

A screen is a failure state when something was refused, timed out, ran out, will not decrypt, cannot
be reached, cannot be done here — or when the input is ambiguous and the product refuses to guess.

Not when it is merely an alternative or an empty result. A search that matched nothing found nothing;
that is an answer. Record the clause, not just the flag, so the register can be argued with.

## policy.json — vocabulary with zones

A word list alone produces false findings: a forbidden word inside a code sample, a filename, or a
screen that is legitimately allowed to use it. Zones are what make the count trustworthy.

```json
{
  "terms": [{ "word": "postage batch", "allow_zones": ["advanced"], "severity": "error" }],
  "zones": { "advanced": { "screens": ["settings-storage"], "selectors": [".adv"] } },
  "scan": { "ignore_selectors": ["code", "pre", ".filename", "[data-verbatim]"] }
}
```

The lint reads rendered text nodes, drops anything inside `ignore_selectors`, then flags a term
outside its allowed zones. Report the count and the board, never a bare total.

## rationale.json — the single highest-value habit

Put the rationale where the screen is made — a docstring, a comment block, a sibling field — and
extract it at build time. The reasoning then physically cannot drift from the screen, because they
are the same object. A reviewer is never looking at a screen without knowing why it is like that,
and there is no separate rationale document going stale in a fortnight.

## What the gate does

1. Loads all eight files. Duplicate keys in the source text are an error — a dict cannot be asked
   about this after the fact, so read the raw text, not the parsed object.
2. Binds every `click` route to text on its source board. Any failure stops the build.
3. Resolves every `to` to a real screen id. Any failure stops the build.
4. Reports, without stopping: places with no empty state, screens with no inbound route, steps in
   `journeys.json` that no screen serves, decisions still `open`.
5. Writes `model/index.json`.

Only route binding and id resolution refuse. Everything else prints a number.
